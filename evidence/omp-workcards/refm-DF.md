## Definitions (verified on disk 2026-11-10; planner probe values below must be reproduced)
- `V = len(cfg.data.metrics)` (= 4: cpu, mem, rx_bytes, tx_bytes; `refresh_study.yaml:data.metrics`), `H = settings.runtime.horizon` (= 120; `timesfm3.yaml`), `settings = load_settings(<normalize.timesfm_config>)`. **Per-pod refresh FLOP** `F(N) = forecast_flops(N, V, H, settings.cost)/1e9` GFLOP (`timesfm_access/flops.py`: analytic matmul-only law, hardware-independent). B2 issues ONE forecast per pod per pass with the pod's `(V, N)` stack (`sequential`/`overlap`: batch 1; `batched_overlap`: `BatchForecaster.predict_pods` = one forward over B pods along the BATCH axis, never packed into `V'=B·V` — `batching.py` docstring) ⇒ identical F per pod in every variant. Cross-check, asserted: `F(5760)=500.975439872`, `F(11520)=1017.897101312` equal the B1 cell `gflop_analytic` of `n{N}-v4` (relative 1e-9).
- **Machine compute G(device, N)** = B1 cell `n{N}-v{V}`: `gflops_s_analytic` (the achieved GFLOP/s of one batch-1 call at the SAME (N, V) shape a pod issues; law FLOP over measured median time so the unit equals F's; `gflops_s_measured` differs by 0.05 %). CUDA: 2459.446 (N=5760), 2597.947 (N=11520). Why this cell: it is the hardware's own measured rate for the call B2 makes, so `budget_s·G/F` is what the machine sustains if the pass were model-bound at that rate; for another machine replace G by ITS B1 cell. Chosen over the probe rate because B1 exists per device/context and the probe only at one context.
